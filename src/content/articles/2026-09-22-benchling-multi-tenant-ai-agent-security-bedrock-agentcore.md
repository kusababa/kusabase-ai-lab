## ニュース概要

AWS Machine Learning BlogがBenchlingの事例を紹介した。Benchlingはライフサイエンス業界向けに研究データ管理プラットフォームを提供する企業で、数千のテナント（顧客）が利用する環境で、AIエージェントが生成した信頼できないコードを安全に実行する必要があった。同社はAmazon Bedrock AgentCoreのCode InterpreterをVPCモードで運用し、Amazon Route 53 Resolver DNSファイアウォールとVPCエンドポイントポリシーを組み合わせることで、DNS経由を含むデータ流出を防ぐ多層防御アーキテクチャを構築した。

## 何が変わったか

従来、AIエージェントが生成したコードを実行する環境は、サンドボックス化されていても外部ネットワークへの意図しない通信（特にDNSクエリを悪用したデータ流出）のリスクが残っていた。Benchlingの取り組みは、Bedrock AgentCoreのCode InterpreterをVPC内に閉じ込め、DNSレベルでの通信も含めて厳格に制御する点が新しい。単一テナント向けの対策ではなく、数千の顧客データを扱うマルチテナントSaaSという文脈で、テナント間のデータ分離とAIエージェントの自由度を両立させる設計思想が具体的に示された。

## 開発者への影響

AIエージェントを実際のプロダクションに組み込もうとする開発者にとって、この事例は極めて実践的な参考資料となる。特に『エージェントが自律的にコードを書いて実行する』機能を提供したいSaaS事業者は、単にサンドボックスを用意するだけでなく、DNSやVPCエンドポイントレベルでの防御まで設計に組み込む必要があることを再認識させられる。Bedrock AgentCoreを使わない場合でも、同様の多層防御の考え方（ネットワーク分離＋DNS制御＋テナント境界の明確化）は自前実装の設計指針として転用可能だ。

## KusaBase視点の考察

この事例が興味深いのは、AIエージェントのセキュリティ課題が『プロンプトインジェクション対策』のようなモデルレイヤーの話に留まらず、旧来からあるクラウドインフラのセキュリティ手法（DNSファイアウォール、VPCエンドポイントポリシー）と地続きである点を示したことだ。生成AIエージェントが『何でも実行できる』自由度を持つがゆえに、攻撃対象領域はモデルの外側、つまりネットワーク層にまで広がる。KusaBase編集部としては、日本の医療・ライフサイエンス系SaaS事業者がAIエージェント機能を本格導入する際、こうした『地味だが本質的なインフラ対策』への投資判断がボトルネックになりやすいと見ている。特に個人情報保護法や医療データのガバナンス要件が厳しい日本市場では、Benchlingのようなマルチテナント設計の透明性ある公開事例は貴重な参照点になるだろう。

## 今後の予測

今後、AIエージェントを組み込んだSaaSプロダクトが増えるにつれ、こうした『テナント分離×コード実行×データ流出防止』の設計パターンが業界標準として整備されていくと予想される。AWSに限らず、GCPやAzureでも同様のマネージドサービスが充実し、開発者はゼロからネットワーク設計を行うのではなく、ベストプラクティスのテンプレートを組み合わせる形が主流になるだろう。医療・ライフサイエンス分野では特にコンプライアンス要件が厳しいため、この種のセキュリティアーキテクチャ事例が今後さらに重視され、日本国内でも同様の実装ノウハウを求める声が高まると見られる。
